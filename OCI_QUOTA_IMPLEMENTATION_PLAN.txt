Personal OCI + hard disk quota: implementation boundary, not deployment receipt
Base: 51a47087f4a55202e2670d168bfc1ecfdc0facaf
Prepared: 2026-10-05 Asia/Shanghai

Observed (metadata-only, no installation/mount change):
- Four Ubuntu 22.04 nodes, kernel 6.8, user namespaces enabled, cgroup v2
  with cpu/memory/pids delegation. All lack Podman, crun, uidmap helpers.
- Package-cache candidate is Ubuntu-maintained Podman 3.4.4 security build;
  this is not proof of a downloaded/installed package or functional runtime.
- 3090 /data and 5090 /data0 are ext4, without project/quota features.
- Both 4090 /data1 volumes are XFS, mounted noquota; xfs_quota is installed.
- Platform logical roots: 3090 /data/amax-console; others /data1/amax-console.
  5090 logical root is a protected NVMe bind. Dataset roots can be separate
  logical aliases of the same filesystem; never sum their capacities.

Selected minimal architecture:
1. Managed rootless Podman, invoked only by trusted node runtime, never expose
   its socket, host CLI, Docker group, privileged mode, arbitrary bind paths,
   host namespaces, devices, hooks, storage options or environment overrides.
   Portal identities remain distinct even though the broker runs as amax.
   Each owner gets a distinct graphroot/control directory under guarded data
   storage. No container store/cache on /home, /var/lib or the system disk.
   The existing shared amax SSH account is administrator access, outside the
   platform isolation promise; do not distribute it to ordinary members.
2. Add an explicit OCI environment mode to existing projects. Development
   shell has a writable image layer (container root can apt install), private
   HOME and the existing project workspace, but zero GPUs. Publish stops the
   development container, commits an immutable image digest and code snapshot.
   Training uses that frozen image/code, readonly dataset leases and existing
   per-job HOME/output directories. No silent conversion of existing venvs.
3. Keep GPUQ ownership of the job unit, limits, GPU UUID allocation and stop
   semantics. Podman must remain in the exact authorized unit descendant
   cgroup (prefer split after a real fixture); user cannot supply device flags.
   Development mounts no NVIDIA devices; training receives only scheduler
   UUID-derived device/CDI entries and trusted driver libraries. Never 'all'.
   Verify conmon/payload ancestry, cancellation, exit status and diagnostics
   rather than assuming rootless Podman automatically preserves these.
4. Kernel project quotas, not statvfs reserve. Per-owner project ID on each
   physical writable filesystem; block+inode hard limits. One ID covers their
   legacy workspace, project dev/env/HOME/runs/releases, personal data workspace,
   direct/relay upload staging, and per-owner OCI graphroot. Metadata/control
   is not mounted to the container. Published data remains charged to its
   explicit billing owner; shared ACL is not silently interpreted as ownership.
   Shared cache/system images use separate bounded pools, not another user's
   quota. Single filesystem budget is shared flexibly, not fixed partitions.
5. Root-only administrative quota provisioner owns durable ID allocation and
   limit changes, restricted to server-derived paths/UUIDs and explicit users.
   It never accepts arbitrary client paths or quota commands. Node user runtime
   reads the resulting verified assignment. Any enabled-but-unverified quota
   fails closed for writes; no fallback to reserve. Linux 6.8 forbids changing
   projid/projinherit from non-initial user namespaces; test this property in
   both bubblewrap and OCI, including hardlink/rename escape attempts.

Small implementation surfaces:
- deploy/personal-oci.py: managed image/container lifecycle and strict argv;
  durable same-ID start/stop/publish, UNKNOWN保留, readonly readiness.
- deploy/storage-quota.py + narrow privileged install/provision helper:
  backing UUID+quota enforcement+project-ID checks; bytes/inodes status.
- Existing ProjectStore / project-ops: OCI metadata and frozen image binding;
  node-executor terminal routes and both runners call the managed backend.
- Every user-write root creation and cross-directory atomic publish must assign
  the same expected project ID before writing. Existing upload/direct-upload,
  snapshot, archive copy and publication paths need explicit cross-projid
  rename tests; project quotas can reject otherwise legitimate renames.
- The root quota policy also pins `database`, `controlRoot` and `logRoot`.
  Native attempt IDs resolve through the scheduler database to the immutable
  platform submission and owner. The attempt control tree and systemd stdout
  file receive that owner's project ID before any payload is launched. This
  closes the otherwise uncharged stdout path; old nonempty logs are not migrated
  automatically. Missing policy/attempt evidence blocks the enabled-quota job.
- API/CLI/UI expose environment kind, image digest, quota usage/limit and a
  clear EDQUOT error. Permission/billing owner derives from trusted identity;
  host-admin root route remains separate and explicitly exempt.

Deployment scope requiring a separate approved maintenance plan:
- Install signed distro Podman/uidmap and rootless runtime/network dependencies;
  explicitly pin package versions after resolving current security support.
- XFS: quotas must be enabled when mounting; current noquota cannot be made
  enforcing by application config. Plan a clean unmount/mount with prjquota,
  draining bind aliases/NFS namespaces and preserving UUID/root inode/guards.
- ext4: enable project/quota and project quota inode offline with e2fsprogs,
  then mount enforcing. No repartition/reformat is proposed; no online tune2fs
  mutation during ongoing Conda/other checksum, no blind remount/reboot.
- Assign IDs to existing owned trees only under quiescence; inventory external
  hardlinks and mixed-owner/shared published data first. Never use username
  display or shared Unix amax ownership as authority to charge/migrate a tree.
- Per-node bounded fixture must prove hard EDQUOT for write/fallocate/mmap and
  inode exhaustion; deleting/releasing data must restore permitted writes.
  Test uploads, apt/pip image writes, outputs/checkpoints, project publish,
  parallel writers and attempts to clear quota IDs. Ensure host reserve remains.
- OCI fixture: apt inside image, no host/etc change; cross-owner deny; no GPU
  in dev; exactly allocated GPU in training; kill/cancel/OOM/diagnostic capture
  and restart identity, immutable release reproducibility. No user execution
  or package installation in the current read-only capability probe.

Compatibility/failure boundary:
Existing venv and bubblewrap mode stay available, accurately labeled. They are
not a full OCI fallback. If quota capabilities or namespace isolation is absent,
hard-quota-enabled users cannot be silently allowed unlimited writes. No unsafe
rootful Docker fallback, no shared socket, no privileged container. Multi-volume
global single hard quota is not atomic; expose per-volume limits unless a later
explicit allocator is implemented. Root-admin/host SSH writes remain out of scope.

Candidate source supports both scheduler runner profiles, OCI development and
immutable publication, resource environment, managed Ray runtime and own GPU
CDI selection. Development can receive trusted PATH/resource variables, never
attempt control mounts. OCI `/dev/shm` is an 8-GiB tmpfs ceiling charged to the
existing unit MemoryMax, matching gpuq-ray's maximum object store.

No production change, package install, quota enablement, mount action or user
container has been performed. Feature flags stay disabled until actual EDQUOT,
rootless package installation, job cancellation and assigned-GPU acceptance.
