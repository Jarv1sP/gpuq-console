# 特殊管理操作申请：设计与实现计划

状态：设计提案，尚未实现或部署。基线：`20dc58f`。普通开发和 GPU 训练不新增审批。

## 使用流程

普通成员在网页「维护申请」或 CLI 提交目标机器、标题、原因、脚本正文、工作目录和超时。申请不执行命令，也不给成员 root 权限。

管理员查看待处理申请和该机器的最新任务／GPU 占用，选择「批准并执行」或「退回」。退回必须写原因。申请者可以撤回待处理申请；修改内容应提交新申请并引用旧编号，不能修改已经确认的脚本。

批准后后台以管理员身份，通过已有 `host.exec/status/cancel` 执行器运行固定脚本快照。申请者无需保持网页或 SSH 连接。申请者和管理员可查看执行状态、退出码、有限长度的 stdout/stderr；其他普通成员不可查看。

## 第一版边界

- 只增加特殊操作申请，不增加原生 SSH、临时 root、跨机调度、自动执行窗口或审批链。
- 已有管理员 root 终端与直接管理命令保留。普通成员的 `host.*` 接口仍然禁止。
- 一个申请只指定一台明确授权的机器，不接受 `auto`，不会故障转移到其他机器。
- 只接受 UTF-8 脚本正文，不接受「批准后再读取成员可修改的脚本路径」。执行为固定 `/bin/bash --noprofile --norc -c SCRIPT`，默认工作目录 `/root`，默认超时 300 秒，允许 1–86400 秒。
- 脚本最多 8 KiB，且需满足现有执行器的 argv 大小限制。标题最多 120 字符，申请／退回原因最多 2000 字符。正文不填写密码或令牌。
- 批准的是脚本字节、目录、超时和机器，不保证脚本引用的外部文件、软件仓库或网络服务不可变。管理员须核对外部依赖，不能宣称任意 root 脚本被安全沙箱限制。
- 这是 root 操作：可能读全局文件、停止训练、绕过 GPUQ。管理员确认前展示当前占用；程序不自动暂停别人的训练，也不承诺失败后回滚。

## 状态与防重复执行

申请状态：`PENDING`（待确认）、`RETURNED`（附理由退回）、`WITHDRAWN`（申请者撤回）、`DISPATCHING`（确认已持久化、可能开始派发）、`RUNNING`、`CANCELING`、`SUCCEEDED`、`FAILED`、`CANCELED`、`TIMED_OUT`、`UNKNOWN`。

1. 创建以「不可变账号 ID + 客户端 UUID」为幂等键；相同键和内容返回原申请，内容不同拒绝。申请编号和节点执行键另由服务端生成，避免成员指定的键与既有管理员命令碰撞。
2. 审批要求当前版本号和预览凭据；两个管理员竞争时只有一个能从 `PENDING` 更新状态。所有审批决定先与审计一起写入 SQLite，再调用节点。
3. 预览只读刷新目标机器状态，显示现有训练、GPU PID 数量和状态是否完整；凭据绑定申请摘要、申请版本、审批人、占用摘要，120 秒有效，门户重启失效。占用摘要包括 GPU UUID／PID、GPUQ 任务 ID／状态、平台未结束任务 ID／状态和完整性，不包括利用率等易抖动指标。批准时重新核验。占用不完整必须额外明确确认「仍执行」，不是视为空闲；不能因为 GPUQ 故障就封死维修入口。快照不是停机锁，仍可能有新的外部操作发生。
4. 申请者和审批人均须启用并获准使用目标机器，审批人须仍是管理员；执行桥和节点 `hostCommand` 能力在批准时核验。检查失败仍留在 `PENDING`，不会假称已执行。
5. 每个申请使用唯一、固定的服务端节点命令键，保存批准管理员的不可变 ID／当时姓名。不把申请者身份改成管理员；审批信息不能由客户端伪造。
6. 正常批准请求派发一次；重试批准只查询原键，不再次 `host.exec`。数据库提交失败不得调用节点。派发响应或结果保存失败、门户重启都按 `UNKNOWN` 处理，仅以原机器／原键核对，绝不自动补发 root 命令。
7. 后台定期查询已派发命令。首次批准／派发与取消由门户现有单进程串行操作队列排序：先撤回／退回则不派发；批准先提交则后续只能停止原命令。重启后任何 `DISPATCHING` 都按待核对处理，不补发。现任管理员可对 `DISPATCHING/RUNNING/CANCELING/UNKNOWN` 请求停止；节点无原回执时仍为 `UNKNOWN`。申请者只可撤回 `PENDING`。停止不是回滚，确认控制组清空前保留非终态。
8. 审批确认事务是授权生效点，此后的账号暂停／降级／删除或申请者撤权不自动撤销已确认操作，即使命令尚未真正启动。门户内部从持久化审批记录取原执行身份，只用于原键 `status/cancel`，无需原账号仍存在；现任管理员可停止，但客户端不能指定该历史身份，后台也不能借此再 `exec`。这是复用现有节点按命令所有者 ID 校验的协议，不给已降级用户权限。申请者失去机器授权后不能新建申请或访问该机器的详情；管理员仍能看到遗留申请。
9. 如节点找不到原命令回执或断网，保留 `UNKNOWN` 和原因，交由管理员核查；不能靠新键自动重跑。管理员也可能显式创建新的操作，平台不承诺跨申请的“完全相同命令永远只执行一次”。

允许的转换：`PENDING → RETURNED/WITHDRAWN/DISPATCHING`；已确认状态经原键核对进入 `RUNNING/CANCELING/UNKNOWN` 或节点确认的执行终态。`UNKNOWN` 可以核对回运行状态或终态，但不能回 `PENDING` 或触发新派发；退回、撤回和执行终态不重启。

## 数据与接口

新增独立 SQLite 表，不修改原训练任务 schema：保存申请快照、创建摘要、申请者、版本／状态、审批人／理由、执行键和最后一次有限结果。审核摘要包含脚本 SHA-256；审计只记录 ID、状态、审批人和摘要，不复制脚本或命令输出。

网页和 CLI 共用 `maintenance.create/list/get/preview/approve/return/withdraw/cancel`。`preview/approve/return/cancel` 仅管理员可用。列表每页最多 50 条；详情才返回脚本和输出；相同账号未完成申请最多 20 条，总记录最多 10000 条，满时拒绝新增，不覆盖历史。输出沿用每路 64 KiB 上限并显示截断标记。不按训练结束删除审批记录，后续人工归档，不承诺自动备份。

客户端不提交 `userId`、角色或批准人；API 从登录会话取得。服务端分别核验所有读写权限，不能只依靠隐藏网页按钮。现有静态 Demo／旧后台缺少能力时隐藏入口或明确提示，不模拟 root 操作成功。

## 实现拆分

1. 本 PR：设计文档，可先独立评审／合并，没有运行时改动。
2. 实现 PR：独立维护申请模块与持久化／审批执行层，网页和 CLI 入口，短使用说明、部署依赖清单与回归测试；以该设计 PR 为基础开发，不等待多机硬件。
3. PR 评审通过后才另行安排升级；本轮不重启线上服务、不创建线上 root 操作，也不拿他人训练验收。

## 验收清单

- 未批准、退回、撤回、越权读写、客户端伪造身份都不调用节点；普通成员仍不能直接 `host.exec` 或进入 root 终端。
- 退回理由必填；脚本快照／摘要固定；版本冲突和过期／占用改变的预览拒绝批准。
- 同键重试、并发批准、门户重启、数据库／审计故障、派发超时和结果保存失败不重复执行；`UNKNOWN` 不是成功或安全重试信号。
- 授权变动、批准管理员降级／删除、请求者撤权、状态过期、旧节点、不完整占用快照、停止未排空分别测试。
- 真实 SQLite、HTTP cookie／CLI bearer 权限、下载客户端、网页提交与退回／批准／状态显示、移动布局、旧训练／项目／数据功能回归。
- 有限输出与错误保持可查看，不把维护错误写成训练失败；升级 COPY 和公开资源映射齐全。节点协议不改时复用现有执行器测试；模拟桥通过不等于生产 root／GPU 实测。
